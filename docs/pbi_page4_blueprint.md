# Power BI: blueprint четвертой страницы

## 1. Что уже сделано в ETL

- собрана витрина `page4_tt_monthly_snapshot.parquet`
- собрана таблица формулы `page4_tt_formula.parquet`
- строка витрины = `месяц + ТТ`
- в конечной витрине оставлены только рабочие бизнес-поля для отчета
- финальная привязка территории ТМ выгружается через `ТМ территория`, `Метод привязки ТМ`, `Доверие привязки ТМ`, `Статус привязки ТМ`
- пилотные и технические поля `AGENCY SV`, raw ID, списки СВ/ТМ и промежуточные признаки используются только внутри ETL и не выгружаются в Power BI

## 4. Связи модели

- `dMonth[MonthStart]` `1:*` `page4_tt_monthly_snapshot[MonthStart]`
- `dRegion[Регион BI]` `1:*` `page4_tt_monthly_snapshot[Регион BI]`

Для фильтрации по ТМ на этом листе использовать финальное поле из витрины:

- `page4_tt_monthly_snapshot[ТМ территория]`
- `page4_tt_monthly_snapshot[Метод привязки ТМ]`
- `page4_tt_monthly_snapshot[Статус привязки ТМ]`

Для фильтрации/диагностики по СВ использовать:

- `page4_tt_monthly_snapshot[Ответственный СВ ТТ]`

Так мы не создаем лишние неоднозначные пути в модели.

Пилотные поля `AGENCY SV`, `ТМ по AGENCY SV`, `ТМ визита`, raw ID и списки участников из конечной витрины удалены, чтобы не раздувать модель и не давать пользователю неоднозначные варианты фильтрации.

## 6. Логика ETL

- база листа строится от `okk_fact`
- `KPI проекта %` на уровне ТТ считается через реальный `kpi_fact`:
  - берем МЕ, которые работали на этой ТТ в месяце
  - подтягиваем их `KPI 1` из KPI-файлов
  - считаем взвешенное среднее по числу визитов МЕ на этой ТТ в месяце
- `Город` вытаскивается из поля `Адрес`
- внутри ETL дополнительно используются визиты МЕ и `AGENCY SV` из клиентской KPI-витрины, но эти технические поля не попадают в конечный parquet
- `ТМ территория` считается по приоритетному правилу:
  - сначала `Регион BI + Город ТТ` сопоставляется с актуальными городами МЕ из `USERS/dim_teams`
  - если город не дает одного ТМ, используется уверенная связка `AGENCY SV + KPI + USERS`
  - если и она неоднозначна, территория не назначается случайно: ставится `Нет надежной привязки ТМ`
- если город из `USERS` и `AGENCY SV` дают разных ТМ, `ТМ территория` остается по `USERS`, но `Метод привязки ТМ = Конфликт: город USERS / AGENCY SV`, а `Доверие привязки ТМ = 60%`
- `Доверие привязки ТМ`:
  - `95%` — один ТМ по городу ТТ из `USERS`
  - `85%` — один ТМ по `AGENCY SV + KPI + USERS`
  - `60%` — конфликт города и AGENCY SV, нужен аудит
  - `40%` — несколько ТМ в городе
  - `35%` — несколько ТМ по AGENCY SV
  - `20%` — регион неоднозначен
- `Ответственный СВ ТТ` заполняется только при уверенной привязке: основной СВ дал минимум `60%` визитов и регион ТТ совпадает с регионом СВ из `USERS`
- если одну ТТ в месяце посещали МЕ разных СВ без явного большинства, `Ответственный СВ ТТ = Несколько СВ / подмена`
- если СВ визита из другого региона, `Ответственный СВ ТТ = Вне региона СВ / подмена`
- для контроля таких случаев в конечной витрине оставлено поле `Тип привязки ТТ`
- если по визитам нет активной привязки МЕ в `USERS`, ставится явный fallback `Нет активной привязки в USERS`
- `Сложность %` считается по методологии страницы:
  - `35%` — повторяемая просадка `KPI проекта %` в истории, усиленная если на ТТ менялись МЕ
  - `25%` — нестабильность `OSA/PICOS` по истории
  - `20%` — повторяемость нарушений `ОКК`
  - `10%` — отклонение от похожих ТТ той же сети и города
  - `10%` — частая смена МЕ на ТТ
- `Score ТТ` — рабочий композит качества ТТ:
  - `55%` текущий `KPI проекта %`
  - `45%` обратная сложность `1 - Сложность %`
- `Статус ТТ` — первая рабочая версия:
  - `Недостаточно данных`
  - `Эталон`
  - `Контроль`
  - `Не вина МЕ`
  - `Сложная ТТ`
- если по ТТ меньше `2` месяцев истории или меньше `3` визитов в истории окна:
  - `Сложность % = BLANK()`
  - `Статус ТТ = Недостаточно данных`
- `Не вина МЕ`:
  - высокая сложность подтверждена
  - но главный вклад в нее дают похожие ТТ / условия точки / частая смена МЕ

---

## 7. Что важно

- `Статус ТТ` сейчас эвристический и может быть откалиброван после просмотра первых месяцев
- `Сложность %` и ее 5 компонент — главная часть листа
- если нужен drill-through в карточку ТТ, лучше строить его от `ТТ + MonthStart`
