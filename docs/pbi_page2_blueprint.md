# Power BI: blueprint второй страницы

## 1. Что уже сделано в ETL

- собрана витрина `page2_actions_monthly.parquet`
- собрана витрина `page2_sv_monthly_snapshot.parquet`
- обе витрины уже содержат:
  - `MonthStart`
  - `YearMonth`
  - `Регион BI`
- значит, лист можно собирать через готовые parquet без сложного DAX

- `dMonth[MonthStart]` `1:*` `page2_actions_monthly[MonthStart]`

## 5. Визуалы второй страницы

### Блок `Рычаги повышения KPI`

- visual: `Table`
- поля:
  - `Что сделать`
  - `Сейчас`
  - `Цель`
  - `Разрыв`
  - `Оценка влияния`
  - `Ответственный контур`
- сортировка:
  - по `Порядок действия`

### Блок `Доказательная база`

- visual: `Table`
- поля:
  - `ДБ заголовок`
  - `ДБ текст`
- сортировка:
  - по `Порядок действия`

Рекомендуемое оформление:

- `Column headers = Off`
- `Totals = Off`
- `Grid = Off`
- первая колонка (`ДБ заголовок`) — более тёмный и крупный текст
- вторая колонка (`ДБ текст`) — меньший и более светлый текст
- строки визуально выглядят как короткие карточки-обоснования справа

### Нижняя таблица

- visual: `Table`
- поля:
  - `Регион BI`
  - `СВ / Объект`
  - `KPI проекта %`
  - `OSA %`
  - `PICOS %`
  - `ОКК %`
  - `Обучение %`
  - `Фрод %`
  - `Риск ухода региона %`
  - мера `m Первое действие команды`
  - `Комментарий действия`

Если нижний visual собран как `Matrix` с иерархией `Регион BI -> СВ / Объект`,
поле `Первое действие` нельзя класть колонкой напрямую:

- иначе Power BI покажет произвольное текстовое значение и на уровне региона
- это неверно, потому что `Первое действие` — атрибут команды СВ, а не региона

Используй меру:

```DAX
m Первое действие команды =
IF(
    ISINSCOPE('page2_sv_monthly_snapshot'[СВ / Объект]),
    SELECTEDVALUE('page2_sv_monthly_snapshot'[Первое действие]),
    BLANK()
)
```

Тогда:

- на строке СВ будет показано действие команды
- на строке региона будет пусто
- на `Всего` тоже будет пусто

## 6. Логика ETL

### `page2_actions_monthly`

- действия считаются на общий месяц
- верхние блоки лучше фильтровать только месяцем, без регионального slicer
- агрегаты считаются по сырым наблюдениям месяца, а не как среднее от средних по регионам
- цели сейчас мягкие:
  - `OSA >= 85%`
  - `PICOS >= 85%`
  - `Обучение >= 75%`
  - `Фрод <= 10%`
- в витрину попадают только действия, где реально есть разрыв до цели
- `ДБ заголовок` = короткое название действия
- `ДБ текст` = шаблонное объяснение:
  - текущий факт
  - целевой уровень
  - 1-2 главные проблемные зоны
- `Сложные ТТ`:
  - ТТ, где одновременно сработали минимум 3 сигнала:
    - `OSA < 80%`
    - `PICOS < 80%`
    - `ОКК < 55%`
    - `Фрод > 10%`

### `page2_sv_monthly_snapshot`

- строка = `месяц + домашняя команда СВ`
- KPI / OSA / PICOS / ОКК / Фрод считаются на уровне `ID супервайзера`
- `Обучение %` считается как накопительный срез по обязательным курсам команды на выбранный месяц через `learning_fact` + связку на `dim_teams`
- `Риск ухода региона %` подтягивается из квартального `enps_fact` на месяц
- `Первое действие` строится без использования риска региона
- `Риск ухода региона %` остаётся только контекстной метрикой
- если `KPI проекта % < 75%`, первое действие = `Разобрать KPI`
- `Комментарий действия` расшифровывает 1-2 главные причины просадки:
  - `ОКК`
  - `OSA`
  - `PICOS`
  - `Фрод`
  - `Обучение`

### Нейминг действий

- `Разобрать KPI`
- `Снизить фрод`
- `Подтянуть ОКК`
- `Подтянуть OSA`
- `Устранить просадку PICOS`
- `Подтянуть обучение`

## 7. Что важно

- лист 2 собран через ETL, без необходимости писать тяжёлые меры
- `page2_actions_monthly` сейчас строится только по KPI-месяцам: `2026-01` → `2026-05`
- `page2_sv_monthly_snapshot` тоже ограничен KPI-месяцами
- если потребуется, позже можно добавить отдельную витрину именно по `региону + месяцу`
- текущая схема остаётся быстрой: page-level витрины маленькие и пересобираются быстро
